# The owner's words behind the core: items 208 onward

How they are kept, and where each item lives: `archive/instructions.md`.

208. **14 November 2026** (the core; the first three quotes in a chat with a session the owner had asked to look
     through the core, not the design session, as that session quoted them on issue #237; the last two to the design
     session, in the message that asked for the queue to be built). Told that work in the core costs every project a
     sync and a reading, that five releases had been cut in two days where about one a week was meant, and shown what
     that session had found in the core:

     > We need to address everything you identified.

     Told that the core's open issues, about twenty, had no order though several waited on another:

     > I mean, you say we need a queue, should we have a queue with it all? And all the thijgs you've brought up?

     The owner agreed to a short file that holds the order alone, each line pointing to its issue, and to that
     session's advice that an orchestrator work the file while it holds items and be stopped once it is empty, with
     nothing released until then. Of a pause on new rules until the first batch was released:

     > And no pause. A pause is me not adding anything.

     To the design session, with the task of building it:

     > The open issues labelled `queued` and `by:chat` were filed today by a chat session I worked with. The decisions
     > quoted in them are mine; treat them as my word.

     > An orchestrator on Opus at high will work the whole file after you, rule changes included, building from those
     > issues. Write `AGENTS.md` and the file so that it can, and tell me plainly if any rule of the floor stands
     > against that.

     Behind "The queue" in `AGENTS.md` and the file `QUEUE.md`: the order in one file and the items in their issues, a
     line joined only on the owner's yes, an orchestrator while the file holds lines, one batch and then one release,
     and no pause written into any rule. Behind the builder who writes a queued rule from the owner's words on its
     issue, which is this repository's difference from `modules/inbox.md`, and behind the trusted builder in
     `SECURITY.md`: every file here is protected, so an orchestrator's builders could change none while that line named
     only the sessions the owner starts. The floor itself stood against none of it: a change to it or to the review
     guidelines still waits for the owner's yes in its pull request (floor rule 3), whoever builds it.
